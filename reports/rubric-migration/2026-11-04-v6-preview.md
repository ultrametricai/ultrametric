# v6 rubric migration preview: two-arena pilot (2026-11-04)

PROMPT_VERSION moved to v6 on 2026-11-03 (c5194785a8, merged in a405c3afd3). The policy
text that landed with it (docs/ACCURACY.md) states that the bump "does not rewrite the
published corpus or authorize a bulk re-judge" and asks for a review of legacy same-source
transitions and the rubric migration before scheduled runs resume. This report is the
measurement half of that rubric-migration review: it quantifies what v6 does to published
verdicts, using the non-publishing `judge-preview` stage. Legacy same-source transitions
(digest-less records) are a separate review this report does not cover.

Companion data: `2026-11-04-v6-preview.json` in this directory carries every flip with old
and new rationales, the quality-only moves, the per-cell pilot failures, and the per-product
rollups.

## Method

- Stage: `pnpm engine judge-preview --category <id> --product <id> --story <id>`, invoked
  once per cell. Per the pilot rules: one provider request per cell, SDK/parse/correction
  retries disabled, 60-second timeout, 40,000-byte input cap. The stage writes no caches,
  verdicts, rankings, or projections.
- Isolation: detached checkout pinned to c5535c5e63, stdout captured outside the checkout,
  `git status` clean before and after all 964 invocations. The two commits between the pin
  and current main (b5a2371a5c) do not touch the pilot arenas or the judge.
- Judge: claude-opus-5-5, prompt v6, interactive transport (the preview stage has no batch
  mode).
- Baseline: each preview verdict is compared to the published verdicts.json row for the
  same cell.
- Arena selection: one arena from each stratum of the fleet.
  - **cloud-platforms** (196 cells, 4 products): published verdicts are the wave-1 v5
    settlement (PR #456) and every judge cache is current under v5, so every delta here is
    purely the v5 to v6 rubric change.
  - **web-scraping** (768 cells, 8 products): published verdicts predate v5, so deltas span
    the v4-era to v6 rubric change. This stratum matches the 20,277-cell backlog that was
    stale under v5 before the v6 bump.

## What v6 changes systematically

v6 adds a required `support` object (relation direct/adjacent/absent, coverage
complete/partial/none, verbatim citations) and enforces it mechanically: credit requires
direct support with at least one verbatim affirmative quote, and full credit requires
complete coverage. The pilot shows five recurring effects, each illustrated in the
companion JSON with full rationales.

1. **Adjacent and building-block credit goes to none.** Example:
   cloud-platforms/aws:agentic-mcp-client, partial(q4) to none(q0). The v5 rationale
   credited Bedrock AgentCore handling MCP connections for hosted agents; the v6 rationale
   classifies that as a developer building block rather than AWS itself acting as an MCP
   client (relation adjacent, coverage none).
2. **Credit inferred from marketing or implication goes to none.** Example:
   web-scraping/firecrawl:rotating-proxy-pool, partial(q3) to none(q0). The v5 rationale
   credited "no proxy headaches" as implying managed proxy rotation; v6 requires an
   affirmative verbatim span documenting the named capability and finds none.
3. **full with an unevidenced story element becomes partial.** Example:
   cloud-platforms/aws:first-party-iac, full(q7) to partial(q7). The capability is direct
   and documented, but one element of the story as written lacks evidence, so coverage is
   partial and the full gate fails. This is the largest single class (44 of 158 flips).
4. **Community-only support loses credit, and contradicted capability can become
   disputed.** Examples: aws:status-incident-transparency, partial(q2) to none(q0) (the
   only support was a community comment); google-cloud and azure
   status-incident-transparency, partial to disputed (documented status pages cited against
   hands-on outage reports from a second tier).
5. **Upward moves happen where the pack already contained verbatim direct support.** 2 of
   158 flips: google-cloud:agentic-scoped-keys partial(q5) to full(q7), and
   oracle-cloud:agentic-nl-commands none(q0) to partial(q3) on a recorded probe of the
   official OCI MCP server.

## Pilot failures

59 of 964 requests returned a first-attempt verdict that failed v6's mechanical
validation. The pilot forbids correction retries, so these cells have no preview verdict:

- 40 proposed full while reporting partial coverage ("full credit requires complete story
  coverage"). In production these would re-run through correction rounds and mostly settle
  at partial or re-justify complete coverage.
- 19 failed verbatim-quote fidelity ("support must quote a cited evidence item verbatim").

First-attempt contract-violation rate: 6.1%. Production judging retains up to three
correction rounds for exactly this class (rankings-engine/stages/judge.ts). Zero API or
transport errors occurred.

## Fleet projection

- Inventory at the pin: 43,685 cells across 104 arenas. Before the v6 bump, 20,277 cells
  in 53 arenas were stale under v5 (computed against cellHash with prompt v5, key v2,
  claude-opus-5-5). Under v6 every cell re-judges on its next judge touch.
- Applying each stratum's pilot flip rate (12.8% to the 23,408 v5-current cells, 18.7% to
  the 20,277 v5-stale cells) projects roughly 6,800 verdict flips fleet-wide, at least 96%
  of them downward, plus a broad downward quality drift on unchanged credit cells (93 moved
  cells, net -33, across the two pilot arenas).
- 586 of 43,685 cells exceed the pilot's 40,000-byte input cap. The production judge path
  has no such cap; only preview-based review is limited there.

## Spend

- This pilot: 964 interactive requests, about 4.2M input tokens and 0.23M output tokens on
  claude-opus-5-5, about $21 (token counts estimated from byte volumes at 3.9 bytes per
  token).
- Full v6 migration via `judge --batch`: about 224M input tokens and 10.4M output tokens,
  about $550 at batch pricing ($2/$10 per MTok), plus roughly $70 of interactive correction
  rounds at the observed 6.1% first-attempt violation rate (correction rounds run on the
  interactive path in the current batch implementation). Total about $620; interactive
  throughout would be roughly double.
- v5-only settlement of the 20,277-cell backlog, which would require reverting the v6
  bump first: about 98M input tokens, about $240 at batch pricing (estimated with the
  smaller v5 prompt and v5-era output sizes).

## Decision inputs

- Ratifying v6 and migrating the fleet costs about $620 batched and moves roughly 6,800
  verdicts, almost all downward, with leaderboard order largely stable in the two pilot
  arenas. The settlement convention for v6 flips (the wave-1 labeled-migration treatment
  from PR #456, or the no-new-evidence revert rule) is an open maintainer call that this
  pilot informs but does not make.
- Settling the v5 backlog instead costs about $240 batched and requires reverting the v6
  bump on main before any judge run.
- The two pilot arenas were chosen for stratum purity. Arenas with heavier community
  evidence or runtime probes may show different flip profiles; the preview stage can be
  re-run per arena at about $0.02 per cell to check any arena before its wave.
