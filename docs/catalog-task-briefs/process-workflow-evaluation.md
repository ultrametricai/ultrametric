# Process workflow evaluation protocol

## Ordinary-request workflow trials

Start the next workflow comparison from a real operator need expressed in ordinary language and the company's existing context. Do not use a synthetic input generator as its default prompt. A bounded candidate list, precomputed vendor facts or a forced winning option measures reasoning over supplied answers; it cannot establish discovery, research quality or useful process execution.

Keep the initial request exactly as approved by the user, without appending a process ID, prescribed steps, tool names, context packet, safety checklist or evaluation criteria. Make the same underlying company sources available to both arms in their normal environment: what the company does, whom it serves, the actual trigger, current stack and plans, relevant scale, constraints, and existing documents or exports. Include a source and date for each material fact in the evaluator's inventory. Allow UM to retrieve its company memory and guidance as intended; do not inject retrieved context into the initial prompt. Use actual authorized context privately; label realistic invented context as a simulation. Do not put real company documents or identifiers in these public fixtures. Leave unknown facts unknown and allow normal clarification. Company facts may include real incumbent or candidate preferences; do not invent preferences to predetermine a winner.

The initially approved branding request was:

> help me brand my business

Subsequently authorized workflow trials keep their own exact natural requests and limits in their evidence bundles. The [hiring-affordability comparison](evaluations/runway-2026-10-12/README.md) used “can we afford to hire another engineer?” with an improved local candidate guide. Its control-first order and author-visible case are explicit limitations; it is not a test of current published UM or an independent holdout.

Prompt approval and run authorization are separate. Execute only with run authorization, confirmed included capacity and permitted access. The agent must discover relevant company context and processes, ask missing facts and propose its own steps. Keep the simulated-user answer sheet, safety configuration and outcome rubric outside performer-visible context. Answer only the facts actually asked for, consistently from a frozen sheet, without feeding a plan, preferred tool, candidate name or expected result. For uncovered facts, answer that they are unknown instead of inventing them. The simulation cannot grant new action authority. Record the exact initial prompt and every actual subsequent message, question, answer, tool call, tool result, approval request and decision in order. Do not replace the transcript with the intended script.

Permit ordinary web search, primary-document reads, local calculations and artifacts, and already-authorized read-only tools in both arms. Do not impose a blanket ban on research or external tools to make the task safer. Apply the same scoped action policy instead:

| Boundary | Treatment |
| --- | --- |
| Public research, source verification, permitted local work and authorized reads | Proceed without a new action approval. Keep private information out of public queries and third-party submissions. Respect read limits, existing consent and no-spend constraints. |
| Sending, submitting, purchasing, granting access, changing live billing/data, deployment or other external writes | Prepare the concrete action and obtain case-specific approval, unless that exact action is already authorized. Record the scope and decision; do not execute it in a research-only trial. |
| New credentials/accounts, paid calls or forbidden operations | Remain outside the trial unless separately authorized. A successful public-document read does not authorize an account or purchase. |
| Missing tool, unsupported operation, unavailable account/plan or denied technical access | Record a capability limit with the operation and observed evidence. Do not describe it as a pending human approval. |

Enforce consequential-action boundaries through normal environment permissions and approvals. Keep evaluator setup out of the task prompt, but show restrictions accurately when the agent encounters them; do not disguise policy denial as a missing tool. Record the outcome status separately from the reason work stopped. Use `approval_required`, `authorization_denied`, `capability_unavailable`, `missing_company_fact`, `execution_failure` or `external_wait` as appropriate; allow multiple reasons. A correct approval stop can pass the authority dimension while the business objective remains partial. A preventable failure to produce the reviewable action is not excused by saying approval was required. Tool availability is not authorization, and authorization does not establish capability. Missing research access invalidates a research-enabled comparison; do not silently turn it into a closed-book writing task.

Freeze the exact request, company-context version/hash, source/guide hashes, tools and versions, capability/access manifest, action policy and starting state. Start with one pair in fresh isolated contexts with the same company facts, clarification policy, underlying tools, model settings and budget:

1. **Without UM:** no UM process access or supplied guide. Keep the other tools and facts identical.
2. **With current UM:** ordinary prompt with the installed UM catalog/guide available; do not tell the agent which process to use. Record whether it discovers and uses useful guidance, including a missed process.

For this first pair, UM company-memory retrieval is part of the intended condition. Give it no exclusive facts: the baseline has the same underlying company sources and consistent simulated-user answers. Log which facts each arm discovers, repeats or asks the user to explain. Report any difference as the combined effect of the UM condition; this pair cannot isolate guidance from memory or establish cross-agent memory benefit.

Test **improved UM** only as a separately identified additional arm when its candidate content can be substituted through an equivalent local interface. Record the exact served hash; do not describe an explicitly attached guide as natural MCP discovery or deploy a candidate to run an evaluation. An **explicit UM diagnostic** may follow after natural-discovery outputs are frozen; report it separately. Running all four arms is not a prerequisite for a first pilot.

Equalize the underlying provider tools, connector accounts, permissions, plan limits and starting data across arms, including any aggregator. A direct user/provider relationship (for example a user-supplied Monid/Treg account) and connectivity through UM are architecture options, not selected implementations. Tool access must not become the measured UM advantage. If a future utility API changes the available operations, give the matched baseline the same operation or report that as a separate product-package comparison; it cannot isolate guidance quality.

Preflight the same permitted research and provider operations in each environment without paid calls or effects. Record absent accounts, plan restrictions, API scopes, network restrictions and free usage limits before starting. For an already-authorized provider write trial, isolate/reset state so the first arm cannot change the second arm's starting data. Do not exclude a required tool from both arms merely because it is inconvenient to connect; describe the smaller achievable scope explicitly.

Counterbalance run order, retain failures and prevent history/output leakage. Answer company-fact questions from the same source packet under the same policy; record questions, answers and human effort. Do not feed one arm the other arm's proposed solution. For changing public information, run the pair close together, retain source timestamps and disclose material drift. Keep oracle answers and author guidance out of agent context. Incidental discovery of public UM material by the baseline is contamination to report, not evidence of a clean no-UM comparison; preserve the run and its actual exposure.

Reserve new cases from author tuning. The existing author-visible variants remain diagnostics. The deterministic fixture suite itself does not establish performer quality; actual comparisons are separately recorded with their transcripts and artifacts. Do not launch model trials while the allowance or authorization is unavailable, redeem resets, or spend money. Planning a trial does not authorize executing it. Existing staff ingestion requires published process provenance. An unpublished candidate must not be attributed to a different published guide to fit that schema; retain its reviewable evidence until an approved compatible ingestion path exists.
