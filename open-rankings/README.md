# Open rankings

The judged vendor evidence behind the rankings: each market directory holds the products
being ranked, the weighted user stories they are judged against, dated evidence packs,
and the verdicts that cite them, together with the scores derived from those inputs. The
site renders this data at [ultrametric.ai/arenas](https://ultrametric.ai/arenas).

## Inside a market directory

Each market lives in `open-rankings/<arena>/`, named by its id in `categories.json`.
Two kinds of file sit side by side: the inputs the judgments rest on, and the derived
outputs computed from them.

The inputs, written by hand or by the engine's evidence stages:

- `products.json` — the products ranked in this market.
- `stories.json` — the weighted user stories each product is judged against.
- `evidence/<product>.json` — dated evidence items (`id`, `tier`, `url`, a verbatim
  `excerpt`, `fetchedAt`) across the claimed-docs, github, community, and probe tiers.
- `claims/<product>.json` — extracted vendor claims with quotes, source URLs, and the
  story ids they bear on.
- `proofs/<product>/` — recorded keyless probe transcripts (paired `.json` and `.txt`)
  behind probe-tier evidence; the protocol is in [`docs/prove-it.md`](../docs/prove-it.md).
- `cert-reports/<product>.json` — conformance-suite reports behind the certification
  registry; the protocol is in [`docs/certification.md`](../docs/certification.md).
- `verdicts.json` — one judged verdict per product-story cell: verdict tier, quality,
  confidence, rationale, and the evidence ids it cites. `pnpm engine judge` writes it,
  cache-keyed on everything about the evidence pack that reaches the judge prompt (each
  item's id, tier, url, and excerpt, plus the prompt and judge-model versions), so
  re-judging unchanged evidence reproduces the same verdicts.

The derived outputs, regenerated by the engine and never hand-edited:

- `rankings.json` — the scored ranking, computed from products, stories, and verdicts by
  `pnpm engine derive --category <id>`. To change a score, change the evidence or
  verdicts, then re-derive.
- `score-history.jsonl`, `score-intervals.json`, `uncertainty.json` — score timelines and
  confidence intervals from the engine's scoring scripts.
- `popularity.json`, `popularity-history.jsonl` — keyless registry and repository signals
  from `pnpm engine popularity`.
- `certifications.json` — the certification registry kept current by the weekly sweep
  over `cert-reports/` (`rankings-engine/scripts/cert-sweep.ts`).
- `pricing.json`, `integrations.json`, `story-tiers.json` — outputs of their engine
  stages and scripts.

Each market carries the core set (products, stories, evidence, verdicts, rankings); the
other files appear where their stage or script has run.

A trimmed verdict from `open-rankings/payments/verdicts.json` reads:

```jsonc
{
  "productId": "adyen",
  "storyId": "accept-card-payment-online",
  "verdict": "partial",
  "quality": 3,
  "confidence": "medium",
  "rationale": "Adyen documents the mechanics of accepting online card payments… Nothing in the evidence supports going live within a day of signing up.",
  "evidenceIds": ["adyen-docs-1", "adyen-docs-14", "adyen-comm-1"]
}
```

## Cross-market files

The files at the top of `open-rankings/` serve all markets at once.

Taxonomy and navigation:

- `categories.json` — the market registry: id, name, description, personas, themes.
- `arena-sections.json`, `arena-icons.json` — index-page grouping and per-market icons.
- `adjacent-arenas.json` — related-market sets behind the alternatives views.
- `search-aliases.json` — search synonyms for markets, stacks, modules, artifacts, and pages.
- `product-families.json` — vendor families and their sub-products.
- `dark-logos.json` — the logos that need dark-mode handling.

Curated layers:

- `ai-stacks.json` — named product stacks by audience.
- `classic-pairs.json` — product pairings the industry expects to work together.
- `hot-products.json`, `popular-products.json` — curated popularity shortlists.
- `icp-types.json` — the customer-profile types the simulator draws on.
- `predictions.json` — open head-to-head predictions with settle dates.

Process-step wiring:

- `step-prompts.json`, `step-vendor-calls.json`, `process-step-stories.json` — the links
  from founder-process steps to markets, products, stories, and runnable calls.
- `graph.json`, `story-graph.json`, `story-edges.json` — the story graph and its
  cross-story dependency edges.
- `human-step-audit.json` — the process steps that stay human, with reasons.
- `mcp-demo-calls.json`, `mcp-endpoint-pins.json`, `live-probes.json` — the recorded MCP
  demo calls, pinned MCP endpoints, and live-probe definitions.

Generated reports:

- `staleness-report.json` — evidence age per market and product.
- `slo-history.jsonl` — dated uptime checks per vendor surface.
- `copy-audit.json` — flagged site copy with file and line locations.
- `assistant-plugins.json` — the assistant-platform plugin sweep.
- `vendor-news.json` — recent vendor blog and changelog items from the radar.

Program queues:

- `arena-roadmap.json` — candidate markets with status and rationale.
- `spike-queue.json`, `spike-priorities.json` — the standing deep-refresh queue and its
  curated priority multipliers (work ordering only; scores stay verdict-computed).
- `oss-candidates.json` — open-source candidates discovered for existing markets.
- `yc-map.json`, `yc-batches.json`, `yc-queue.json`, `yc-rejections.json` — YC company
  mapping and the coverage queue built from it.

## How the site and CI read it

`lib/data.ts` loads a market: `loadCategory` schema-parses products, stories, verdicts,
rankings, and each product's evidence, and picks up the optional files (popularity,
claims, uncertainty, certifications, vendor responses) where they exist. The cross-market
files have their own loaders in `lib/` (for example `lib/arenaSections.ts`,
`lib/storyGraph.ts`, `lib/popularRanking.ts`). The private site repo materializes this
open surface at a pinned commit via `scripts/sync-open.mjs` and `open-manifest.json` and
renders it at ultrametric.ai. In CI, `pnpm test` validates each file against its schema
(`lib/schemas.ts`, `schemas/`), and `pnpm recompute-check` rebuilds the rankings for each
market from the on-disk inputs and deep-compares them against the committed
`rankings.json`.

## Contribute

- [The verdict contest flow](../CONTRIBUTING.md#1-contest-a-verdict) — a prefilled issue
  per verdict; the fix is new evidence, then
  `pnpm engine judge --category <id> --product <id>` and
  `pnpm engine derive --category <id>`.
- [The evidence PR flow](../CONTRIBUTING.md#2-add-evidence-pr-flow) — add an evidence
  item, re-judge, and commit the evidence, `verdicts.json`, and `rankings.json` changes
  in one PR.
- [The new-product guide](../CONTRIBUTING.md#add-your-vendor) — add a product to an
  existing market.

Gates before any PR here: `pnpm test` (schema validation) and `pnpm recompute-check`
(derived data deterministic).

## Reviews

`reviews/` is the review layer over the judged rankings: `reviews/generated/` holds one
dated, machine-readable review per judged product, emitted deterministically from the
committed ranking data, and the directory root takes hands-on human reviews in the same
schema. The rubric, disclosure rules, and regeneration gate are in
[the reviews README](reviews/README.md).

## Experiments

`experiments/` holds runtime and prototype output kept structurally separate from the
evidence-judged markets. `experiments/depth/` holds Agentic Depth Program runs: dated
per-target reports and transcripts from the runtime conformance and task-trial ladder
designed in [`docs/agentic-depth-program.md`](../docs/agentic-depth-program.md).
`experiments/computer-use/` holds the computer-use feasibility study, one JSON result and
screenshot per attempted signup or filing flow, summarized in `feasibility-report.json`
([`docs/computer-use-feasibility.md`](../docs/computer-use-feasibility.md)). `gpus.json`
and `processors.json` are hardware spec-comparison prototypes curated from vendor spec
sheets, outside the judged markets.

This area's maturity grade and known gaps are tracked in [`coverage/index.json`](../coverage/index.json).
